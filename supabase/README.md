# BusyBuddy server (Supabase + PowerSync)

Server side of the offline-first backend. Each device keeps a local SQLite copy
and syncs it with this Postgres database through PowerSync. Several devices or
staff can share one shop.

- `migrations/`: schema, row-level security, server functions, and the
  `powersync` publication.
- `tests/`: pgTAP tests.
- `../powersync/sync-rules.yaml`: PowerSync sync rules, with one bucket per shop.

## Running locally

You need the [Supabase CLI](https://supabase.com/docs/guides/local-development)
and Docker.

```
supabase start        # local stack; applies migrations on first start
supabase db reset     # re-create the database from migrations/
supabase test db      # run tests/*.sql with pg_prove
supabase stop
```

Each test file runs in a transaction that it rolls back. The tests insert their
own `auth.users` rows. They act as a user with
`set local role authenticated` plus `set local request.jwt.claims = '{"sub":"<uuid>"}'`.

## PowerSync

1. Create a database role for PowerSync. The migration does not create it,
   because the role needs a password:
   ```sql
   create role powersync_role with replication bypassrls login password '<secret>';
   grant select on all tables in schema public to powersync_role;
   ```
2. Point the PowerSync instance at the database. Use Supabase Auth (JWT `sub`
   is `request.user_id()`) and deploy `powersync/sync-rules.yaml`.

Sync rules: one bucket per shop. The bucket parameter is each `profile_id` the
user has in `shop_member`. The bucket holds that shop's `business_profile`,
`shop_member`, `product`, `product_variant`, `customer`, `sale`, `sale_item`,
`expense`, `supplier`, `stock_alert` and `code_conflict` rows. `shop_invite`
is not synced.
`shop_member` has no single-column key, so it syncs with
`id = profile_id || ':' || user_id`.

PowerSync Service now marks `bucket_definitions` (Sync Rules) as deprecated in
favour of Sync Streams. These rules still pass the PowerSync validator.
Moving to Sync Streams is a later change.

## Data conventions

These match the on-device schema (`lib/core/db/database_helper.dart`):

- Ids are `text` UUID strings generated by the app. The exception is
  `stock_alert.id` and `code_conflict.id`: the server generates them.
- Money is `bigint` minor units (`*_minor`). Flags are `smallint` 0/1.
- Timestamps are `text`, UTC ISO-8601 with milliseconds and a `Z`, e.g.
  `2026-11-10T08:30:00.123Z`. This is the format of `toDbTime`.
  `public.to_db_time(timestamptz)` gives the same format, and column defaults use it.
  Calendar dates (`expense.date`, `product.expiry_date`) are `YYYY-MM-DD`.
  The client always sets `expense.date`.
- Every shop table has `profile_id`. That includes `product_variant` and
  `sale_item`, which have no `profile_id` on the device yet.
- Child rows reference parents through composite `(id, profile_id)` foreign
  keys, so a row cannot reference another shop's data.
- `backup_log` and `business_profile.google_account_id` are not ported.

## Access rules

All tables use row-level security. `anon` has no table access and cannot run
any of the functions below.

| Table | Members (owner or staff) | Owner only | Functions only |
|---|---|---|---|
| `business_profile` | select | update | insert (`create_shop`) |
| `shop_member` | select | | insert (`create_shop`, `join_shop`) |
| `shop_invite` | | | all (`create_invite`, `join_shop`) |
| `product`, `product_variant`, `customer`, `sale`, `sale_item`, `expense`, `supplier`, `stock_alert`, `code_conflict` | select, insert, update, delete | | |

A direct update of `business_profile` still goes through the currency lock
(see `update_profile`).

## Client write contract

The PowerSync upload connector should map local changes as follows:

- **Sales**: upload a new local `sale` together with its `sale_item` rows as
  one `record_sale` call. Do not insert them directly. A direct insert does
  not change stock.
- **Stock changes**: use `adjust_stock`, or let `record_sale` do it. Never
  upload `product.stock_qty` or `product_variant.stock_qty` as an absolute
  value in an update. Devices change stock concurrently, and an absolute
  write would overwrite another device's change. A new product or variant may
  carry its initial `stock_qty` on insert.
- **Profile**: `update_profile`, or a direct update by the owner.
- **Products, variants, customers, expenses, suppliers**: direct
  insert/update/delete. Archive products (`archived = 1`) rather than
  deleting them: a product used in a sale cannot be deleted.

## Duplicate SKUs and barcodes

Devices create products offline, so two devices can give two active
products of one shop the same SKU or barcode. The server accepts the
duplicate. A rejected upload would block every later upload from that
device, sales included. Instead, the server flags the duplicate in
`code_conflict`:

- The `product_code_conflicts` trigger runs on product insert, and on any
  update of `sku`, `barcode` or `archived`. It adds one row for each other
  active product of the shop with the same non-null code. The row holds
  `product_id` (the product whose write made the duplicate),
  `other_product_id`, `field` (`sku` or `barcode`) and `value`.
- An open conflict (`resolved_at` null) is resolved automatically when either
  product is archived or its code changes. Un-archiving a product flags any
  duplicates again. Members may also set `resolved_at` themselves.
- Archived products never conflict. The same code in another shop is not a
  conflict.

The client keeps its own local duplicate check for instant feedback. It
shows open `code_conflict` rows to the owner.

## Server functions

All are `security definer` and callable by `authenticated` users, e.g.
`supabase.rpc('record_sale', {sale: {...}, items: [...]})`. Errors use these
SQLSTATEs:

- `42501`: not signed in, or not a member/owner.
- `22023`: bad argument, or an invalid invite.
- `P0002`: product or variant not found.
- `23514`: currency locked, or a CHECK failed.
- `23505`: unique conflict on an id.
- `23503`: foreign key, e.g. another shop's product.

### `create_shop(profile jsonb) returns business_profile`

Inserts a `business_profile` row and makes the caller its `owner`.

- `profile` needs `id`, `name` and `type`. Other columns are optional and take
  their defaults when omitted (`currency` `INR`, `currency_decimals` 2, and so on).
- If the caller already owns a shop with this id, the call returns that shop
  and changes nothing, so retries are safe.
- If another user owns the id, the call fails with `23505`.

### `record_sale(sale jsonb, items jsonb) returns jsonb`

Records a sale that already happened on a device. In one transaction it
inserts the sale and its items, then decrements stock relatively:
`stock_qty = stock_qty - qty`.

- `product.stock_qty` goes down for every item.
- `product_variant.stock_qty` also goes down for items with a `variant_id`.

Arguments:

- `sale`: `sale` columns. `id` and `profile_id` are required. A missing
  `created_at` defaults to now.
- `items`: an array of `sale_item` columns (`id`, `product_id`,
  `product_name`, `variant_id`, `qty`, `unit_price_minor`, `cost_price_minor`).
  Each item's `sale_id` and `profile_id` come from `sale`.

Behaviour:

- **Idempotent on `sale.id`.** If the sale already exists, the call changes
  nothing and returns `duplicate: true`. A retried upload never counts twice.
- **Never rejected for stock.** If the shop's `allow_oversell = 0` and the
  sale leaves stock below zero, the call adds a `stock_alert` row for that
  product or variant. It adds one row per variant below zero
  (`variant_id` set) and one per product whose total is below zero
  (`variant_id` null). The row records `stock_after`. With `allow_oversell = 1`
  stock goes negative and no alert is written.
- **Missing references do not fail the sale.** Another device may have
  deleted the customer or variant. In that case, the sale is stored with
  `customer_id` or `variant_id` null, as `ON DELETE SET NULL` would have done.
  The same applies to a customer of another shop, or a variant that does not
  belong to the item's product. The product total is still decremented. No
  variant stock changes for such an item.
- An item with no `variant_id` for a product that has variants is accepted.
  It decrements only the product total.
- **Fails as a whole** only if an item's product is not in the shop
  (`23503`). Products are archived, not deleted, so this means a bad id.
- Sales of one shop are serialised on the shop's `business_profile` row.

Returns `{"sale_id": "...", "duplicate": false, "stock_alerts": 0}`.

### `adjust_stock(product_id text, variant_id text, delta bigint) returns jsonb`

Changes stock relatively, for a restock or a correction. `delta` may be
negative, and stock may go below zero.

- With `variant_id` null, it changes only the product. A product that has
  variants refuses this with `22023`, because its total must stay the sum of
  its variants.
- With `variant_id` set, it changes the variant and its product's total by
  `delta`. The variant must belong to the product.

Returns `{"product_stock_qty": n, "variant_stock_qty": n | null}`. Fails with
`P0002` if the product is not in one of the caller's shops.

### `update_profile(profile jsonb) returns business_profile`

Owner only. `profile` holds `id` plus the columns to change. Omitted columns
keep their value, and `id` and `created_at` are ignored.

A change to `currency` or `currency_decimals` fails (`23514`, "Currency is
locked once products or sales exist") once the shop has any product
(archived included) or any sale. This mirrors
`ActiveProfileNotifier.updateProfile`. A trigger enforces the same lock, so
it also holds for direct updates.

### `create_invite(profile_id text) returns text`

Owner only. Returns a 10-character single-use code, valid for 7 days. The
code uses `A-Z` and `2-9` without `0`, `O`, `1` or `I`.

### `join_shop(code text) returns text`

Adds the caller to the code's shop as `staff`, marks the invite used, and
returns the shop's `profile_id`.

- Case and surrounding spaces in `code` are ignored.
- An unknown, used or expired code fails with `22023`.
- A caller who is already a member of that shop gets the `profile_id` back,
  and the invite is not used up.
